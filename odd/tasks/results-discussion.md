# Results discussion: hypotheses, tests, novelty and qualitative analysis per stage

Objective: the experimental protocol deliberates performance measures and the discussion to produce; the proof of concept and the full experiments each close with one checked `Results/discussion.json` (hypothesis verdicts backed by tests, novelty justification, qualitative/interpretability analysis, summarized discussion), and the dashboard shows it per stage and gates sub-phases 5.8/5.11 on it.
Branch: `feat/results-discussion` (from `main` c4fbfe6e, tag v0.43.0). Delivery: release 0.44.0, merge, push, delete branch, GitHub release, update local `smith` (pipx) and the QMLEEG workspace. Tests: `.micromamba/envs/papersmith/bin/python -m pytest -q -n 6`; `npm test`.

## Specs

- S0. The operator's requests, verbatim: see L1 and L2.
- S1. **Contract module and CLI** `skills/_core/results/discussion.py` (stdlib only, importable by file path; no package `__init__` assumed) plus `skills/_core/results/discussion_cli.py`. Each CLI verb prints exactly one JSON object; a refusal prints `{"ok": false, "error": <CODE>, "message": ...}` and exits non-zero; nothing is written on refusal. Verbs:
  - `scaffold --product <path to implementations/<repo>/<Name>>` writes `<Name>/Results/discussion.json` with `status` fields left pending: stage from the holder (`Experimental_AGREED.md` → `full`, else `AGREED.md` → `poc`, else refuse `PRODUCT_ABSENT`/`APPROVAL_ABSENT`); `protocol` = the latest `experiments/experiments-*-vNN.md` under the forge/workspace root (the product's `../../..`), one hypothesis entry per `## Experiment [exp:E#]` with its declared **Hypothesis** and **Success criterion** copied verbatim, verdict `pending`, `observed` empty; one `metrics` entry per metric name found in the significance rows/tables is NOT required -- metrics may start empty; the list of existing figures/tables/significance comparisons is written under `available_evidence` to help the author. Never writes a number it did not read. Refuses `DISCUSSION_EXISTS` when the file exists (no overwrite flag).
  - `check --product <path>` validates and prints `{"ok": true|false, "status": "complete"|"draft"|"invalid", "errors": [...], "warnings": [...], "stage": ...}`; exit 0 for complete or draft, non-zero for invalid or absent (`DISCUSSION_ABSENT`).
  - `status --product <path>` same as check but always exit 0 when the product exists.
- S2. **Schema 1** of `Results/discussion.json`:
  `{"schema": 1, "stage": "poc"|"full", "protocol": "<relative path>", "generated_at": "<ISO>", "summary": "<summarized discussion, 1..2000 chars>", "discussion_type": ["comparative"|"ablation"|"failure-analysis"|"sensitivity"|"interpretability"|"cost"|"generalization", ...], "metrics": [{"name", "role": "primary"|"secondary", "why", "source"}], "hypotheses": [{"id", "experiment", "statement", "metric", "test", "criterion", "observed", "evidence": ["<path relative to the product>" | "significance:<comparison>"], "verdict": "supported"|"partially_supported"|"not_supported"|"inconclusive"|"pending", "rationale"}], "novelty": {"claim", "verdict": "justified"|"partially_justified"|"not_justified"|"pending", "evidence": [...], "rationale"}, "qualitative": [{"title", "kind": "qualitative"|"interpretability"|"explainability", "method", "figure": "<path relative to the product>", "reading"}], "qualitative_not_applicable": "<reason>", "limitations": ["..."], "next_steps": ["..."]}`.
- S3. **Check rules** (`invalid` = any error): wrong/missing `schema`; `stage` disagreeing with the holder; empty `summary`; no `metrics` or a metric without `name`/`why`; no `hypotheses`; a hypothesis without `id`/`statement` or with a verdict outside the enum; a non-pending, non-inconclusive verdict without evidence; an evidence path that does not exist inside the product folder (or escapes it); a `significance:<comparison>` that matches no `comparison` in the product's `Results/**/significance*.json`; at stage `full`, a `supported`/`partially_supported`/`not_supported` verdict citing no `significance:` evidence (the hypothesis test is mandatory in the full run; at `poc` it is a warning); `novelty` missing or verdict outside the enum, or a non-pending novelty without evidence; neither `qualitative` (non-empty) nor `qualitative_not_applicable` (non-empty); a qualitative entry with a `kind` outside the enum or a `figure` that does not exist. `draft` = valid but some hypothesis or the novelty is `pending`. `complete` = valid and nothing pending. Unknown keys are warnings, never errors.
- S4. **Significance rows** may carry optional `hypothesis` and `experiment` keys; the dashboard reads and shows them.
- S5. **Qualitative artifacts** live under `Results/qualitative/**` (png/svg/jpg/pdf); the dashboard shows them in their own gallery (kind `qualitative`), never mixed into generic figures.
- S6. **Doctrine, protocol** (`skills/experimental-deliberation/SKILL.md`): the tutor deliberates (a) each performance measure, why it answers the hypothesis and which is primary; (b) a hypothesis matrix per experiment: hypothesis → metric → test → success criterion → which verdict each outcome yields; (c) the novelty claim and which comparison justifies it; (d) whether a qualitative / interpretability / explainability analysis applies (method, what it should show) or why not; (e) the type of discussion each experiment will produce (from S2's `discussion_type`). The artifact section lists these in the per-experiment order. No engine (TypeScript) change.
- S7. **Doctrine, PoC and full** (`skills/proposal-implementation/SKILL.md`, `skills/experimental-implementation/SKILL.md`, their `references/usage.md` where results are listed, agents `.claude/agents/implementation-build.md`, `experiments-build.md`, `experiments-reviewer.md`): when the results are in, run `discussion_cli.py scaffold`, fill every field from the results on disk (never inventing a number; a verdict follows the declared criterion and test), run `check` until `complete`; the Results layout table gains `Results/discussion.json`, `Results/qualitative/**` and the significance `hypothesis`/`experiment` keys; the reviewer checks that each verdict follows from its test. `experiments-tutor` mentions it can explain the discussion.
- S8. **Dashboard view** (`experiments_view.py`): each product gains `discussion`: `null` when absent, else `{file, status, errors, warnings, stage, summary, discussion_type, metrics, hypotheses, novelty, qualitative, qualitative_not_applicable, limitations, next_steps}` (bounded, clipped, read through the contained reader; status from S3 via the shared module); `qualitative` figures list; significance rows with `hypothesis`/`experiment`. The view gains `stage_comparison`: per hypothesis id, the verdict at PoC and at full (from the latest products of each kind).
- S9. **Dashboard render** (`experiments-panel.js`, `i18n/es.js`, `i18n/en.js`, styles if needed): every product card opens with a "Resumen y discusión" / "Summary and discussion" block: status badge (complete/draft/invalid + errors), summary, discussion types, hypothesis table (id, experiment, statement, metric, test, criterion, observed, verdict badge, evidence links to `/api/artifact` for paths), novelty verdict, metrics table, qualitative gallery with title/method/reading, limitations, next steps. Absent file: an empty state naming the command `python skills/_core/results/discussion_cli.py scaffold --product <path>`. A "PoC vs Completo" comparison section when both stages exist. Everything escaped.
- S10. **Gating** (`server.py`): sub-phase 5.8 passes only when at least one PoC product has a `complete` discussion (ACTIVE when a PoC exists); 5.11 likewise for full products; Phase 5 status and progress use these; 5.12 reads `Results/reviewer_report.json` (PASS when present with `status` `resolved` or all blockers resolved, ACTIVE when present otherwise, PENDING when absent) and its detail no longer says it leaves no file; `G-EXP-POC` criteria mention hypothesis verdicts, hypothesis tests, novelty and the summarized discussion. Details state the counts (e.g. "1 of 2 with a complete discussion").
- S11. Docs: CHANGELOG `## 0.44.0` (also record that 0.43.0 shipped the execution monitor and that its version literals were left behind), `docs/skills.md`/`docs/cli.md` where results/skills are described, README Phase 5 if it lists Results artifacts; CLAUDE.md/OPENCODE.md/template text only through the repository's projection scripts.
