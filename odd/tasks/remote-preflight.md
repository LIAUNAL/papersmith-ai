# Remote preflight: catch locally what QMLEEG's rehearsals caught remotely

Objective: everything that failed or cost a release round while configuring QMLEEG's full experiments for Kaggle and Colab is checked locally, in one command, before the first remote rehearsal; the lessons are written into the flow (skills, agents) so future projects configure and launch in one pass.
Branch: `feat/remote-preflight` (from `origin/main` 5b7b447e, v0.35.0). Delivery: release after verification on the operator's word. Tests: `~/Documents/papers_smith/papersmith-ai/.micromamba/envs/papersmith/bin/python -m pytest -q -n 6`; `npm test`.

## Specs

- S0. The operator's requests, verbatim (2026-10-28): "si" to "¿Abro un feature en papersmith con 1, 2 y 3 después de la release 0.33.0?" (1 = un chequeo previo en un solo comando, 2 = el dataset como entrada declarada del job, 3 = generar todos los jobs de una vez a partir del reparto de `schedule`); and "asgurate de configurar para lanzar los experimeintso en kaggle, y luego, todas las iteraciones, erroes y aprendizajes, dejarlos en el flujo de smith para ahorrar tiempo y ejecuciones en futuras corridas".
- S1. `remote_cli preflight --target <repo> --entrypoint <job runner.ipynb> [--worker <id>]` (read-only on the remote; never submits) reports one row per check with `pass|fail|warn`, the evidence, and the exact fix command, and exits non-zero on any `fail`. Checks, each from a lesson in the Log:
  - (a) diagrams: every approved kind validated (else names both routes: dashboard button or chat `validate`) — L2;
  - (b) interpreter: the driver for the job's service is importable by the interpreter `submit` will use, or the fix names the workspace env interpreter — L3;
  - (c) code reachability: the repository URL is anonymously reachable, or the job carries a code bundle, or the service carries a repo credential and one is declared — L4;
  - (d) inputs: a kernel service job whose target code reads a public dataset declares it with `--input-dataset` (warn when the job declares none and the workspace dataset registry names a remote source) — L5;
  - (e) local rehearsal: runs the job's declared smoke function locally in a scratch directory under runner-like conditions (`FORGE_RUN_MODE=smoke`, the job's code materialized exactly as the worker will see it — from the code bundle when there is one, so no git metadata beyond `.git/HEAD`; `FORGE_CLONE_ROOT`/`FORGE_CLONE_COMMIT`/`FORGE_INPUT_DATASETS` set as the runner would; workspace-only paths unavailable), with a time budget, then checks the `shard.json` it leaves carries every `requiredEvidence` path — L6, L7. It may accept target-declared smoke kwargs for a cheaper local scale (e.g. `--local-smoke-kwargs`), and reports how long it took;
  - (f) accounts: the worker's account authenticates / is signed in (reuse the existing validate/sign-in probes; no new credential reads) and has its own readiness or needs a rehearsal — L8;
  - (g) accelerator: names the accelerator the job will request on that service (e.g. the default variant) so a mismatch with the plan is visible before spending quota — L9;
  - (h) session fit: each unit's upper-bound estimate (when a timing record exists) fits the service's session margin or the job declares carry paths — existing `schedule`/`assess` rules.
- S2. Datasets as declared job inputs from the workspace registry: `generate-job --dataset <slug>` resolves `datasets/registry.json` + the slug's preparation: a public remote source becomes `--input-dataset <owner/slug>` (kernel services) and is recorded with the preparation's sha256 values so the target can verify; a private/unpublished source refuses with the fix (`/datasets publish` with consent) — no data is uploaded by this command.
- S3. `generate-jobs --from-schedule <plan.json>` (or the existing `schedule` output) generates every remote step's job in one call: service from each step's declared `service`, clone paths and notebooks from the step, environment requirements from the target's pinned dependencies minus those the service image already provides when the adapter declares them (else all), carry paths from the step's `produces`, code bundle automatically when the repository is not anonymously reachable and the service carries bundles, inputs from S2. Prints one row per job and the single preflight command to run next. Existing single `generate-job` unchanged.
- S4. Lessons in the flow: the remote-execution SKILL.md gains a "Before the first rehearsal" section listing the preflight and each lesson in the Log as a rule; the walk/build agents and both implementation skills run `preflight` before asking the operator to authorize a rehearsal; the kit scaffold's `remote_stamp.py` falls back to `FORGE_CLONE_COMMIT` when `git rev-parse` fails (L7) and the scaffold's smoke template stamps `shard.json`. Doctrine files must not name a service.
- S5. Docs, help, CHANGELOG `## Unreleased`.
