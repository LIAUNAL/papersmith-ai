# Carry a previous session's output into the next kernel automatically

Objective: a resumable unit continued in a new session gets the previous kernel's output (checkpoints, per-unit records, studies) mounted and restored automatically, instead of a hand-written `kernel_sources` entry.
Branch: `feat/kernel-carry` (from `origin/main` 6e741b20, v0.31.0). Delivery: one release after verification; push, merge and release are the operator's. Tests: `~/Documents/papers_smith/papersmith-ai/.micromamba/envs/papersmith/bin/python -m pytest -q -n 6`; `npm test` (node_modules linked).

## Specs

- S0. The operator's request, verbatim (2026-10-28): "ajusta pendiente 1", where pending 1 was: "papersmith todavía no adjunta automáticamente la salida del kernel anterior en Kaggle. La prueba en vivo confirmó que funciona, pero hoy hay que declararlo a mano."
- S1. Declared carry paths. A job declares the paths (relative to the product folder) whose contents a continuation needs, e.g. `Results/e1/runs`, `Results/checkpoints`, `hpo/studies`; `generate-job` accepts them (repeatable flag) and records them in the job's config. A job that declares none behaves exactly as today.
- S2. Automatic attach on continuation. When `submit` sends units that an earlier submission of the same entrypoint, on the same worker, left remaining (the same evidence `remaining` reads: a settled submission whose `partial.json` lists them, or a kept partial), the kernel service adapter adds that earlier submission's kernel ref (`<owner>/<slug>`) to the pushed metadata's `kernel_sources`, without the operator writing it. The ledger's `submitted` event records the carried-from submission id and ref.
- S3. Restore before the entrypoint. In the kernel, before the entrypoint runs, the runner copies each declared carry path from the mounted input root `/kaggle/input/notebooks/<owner>/<slug>/` (live-verified prefix, L3 of session-checkpoints) into the working product folder, so the target resumes from checkpoints already on disk and the target code is unchanged. It also exports the mount path in an environment variable (e.g. `FORGE_CARRY_IN`). A missing mount or missing path is reported in the run log and the unit starts fresh; it is never fatal.
- S4. Same account only. A private kernel's output is only verified to carry within its own account. A continuation unit whose checkpoint was produced on another worker is refused at `submit` with a typed error naming that worker and the flag that starts it fresh instead (`--no-carry`); `distribute` places continuation units on the worker that produced them when that worker is in the pool.
- S5. Services without kernel inputs (Colab) are unchanged and say so: a continuation there carries nothing automatically, and `submit` reports `carry: unsupported` for that service rather than silently dropping it.
- S6. Docs: remote-execution SKILL.md and references, help text, CHANGELOG `## Unreleased`; the agent rule "Every remote unit fits one session, or resumes" mentions that the carry is automatic for declared paths (doctrine files must not name the service; see session-checkpoints L4).
